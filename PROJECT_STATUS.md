# Состояние проекта

> Актуально на 24.07.2026. Полный аудит выполнен по исходному коду, IPC, UI, зависимостям, производительности и доступным smoke-проверкам.

## 1. Общая информация

- Название проекта: Gitora
- Цель проекта: десктопное приложение для визуального просмотра истории GitHub-репозиториев и выполнения основных операций GitHub.
- Используемые технологии: React 19, TypeScript, Vite, Electron 42, Tailwind CSS 4, Lucide React, Vitest, MCP SDK.
- Версия: 0.1.12 (по `package.json`).
- Основная архитектура: Electron shell с context-isolated preload-мостом, React UI, общий `AppContext`, GitHub API в Electron main process, отдельный MCP-сервер.
- Хранилище данных: постоянной базы данных нет; GitHub остаётся источником данных, настройки UI хранятся в `localStorage`, сессия Electron хранится через `safeStorage` в `app.getPath('userData')`.

## 4. Что сломано или требует исправления

### ✅ Исправлено: рассинхронизация сессии Electron и MCP

Описание: Electron сохраняет зашифрованное содержимое через `safeStorage` в `app.getPath('userData')/github-session`. MCP больше не читает этот файл и получает результаты GitHub-запросов через локальный IPC-мост.

Где находится: `electron/main.cjs`, `electron/mcpBridge.cjs`, `mcp-server.cjs`.

Что изменено: main process запускает bridge с random secret и metadata-файлом, MCP отправляет только разрешённый API endpoint; токен не передаётся MCP и не хранится открытым текстом.

Результат: MCP tools используют текущую Electron-сессию, logout прекращает доступ без удаления bridge, а старый plaintext-поиск `github-session` удалён.

Оставшийся риск: bridge metadata содержит локальный random secret для доступа к сокету; файл не содержит GitHub-токен и создаётся с режимом `0600` там, где ОС поддерживает режимы.

### ✅ Защищённая загрузка release asset

Описание: IPC `app:download-release` принимает URL из renderer, поэтому адрес нужно проверять до сетевого запроса и при каждом редиректе.

Где находится: `electron/main.cjs`, `electron/githubErrors.cjs`, `electron/githubErrors.test.mjs`.

Что изменено: добавлен `isAllowedGitHubDownloadUrl`; разрешены только HTTPS `github.com` и `objects.githubusercontent.com`. Загрузка использует ручные редиректы с проверкой каждого `Location` и ограничением в три перехода.

Оставшийся риск: размер release asset пока не ограничен жёстким лимитом; это отдельная задача hardening.

Дополнительно: IPC теперь проверяет номера PR/issue как положительные безопасные целые числа, а `app:download-archive` принимает только полный 40-символьный hexadecimal SHA.

### ✅ Валидация Git refs для веток

Описание: UI может работать с ветками вида `feature/my-feature`, поэтому имя ветки нельзя проверять тем же правилом, что owner и repo.

Где находится: `electron/main.cjs`, `electron/githubErrors.cjs`, `electron/githubErrors.test.mjs`.

Что изменено: добавлен отдельный Git ref validator. Он разрешает slash-сегменты, но отклоняет пустые сегменты, `..`, `@{`, небезопасные точки и `.lock`. Удаление и переименование используют безопасное кодирование сегментов.

Результат: создание, удаление и переименование веток с `/` проходят через единый безопасный путь; SHA исходного коммита при создании ветки также проверяется.

### ✅ Ручная и полная синхронизация с GitHub

Проблема: после изменений на GitHub Gitora обновляла commits и branches только при смене проекта, а branch mutations не перерисовывали граф.

Причина: загрузка snapshot находилась внутри `useEffect`, отдельного refresh use case не было; кэширования при этом не обнаружено.

Решение: добавлены два связанных потока. `refreshRepositoryData()` обновляет snapshot открытого репозитория. `syncAllData()` сначала заново получает список репозиториев GitHub, добавляет новые и удаляет отсутствующие, затем обновляет выбранный snapshot, branches, commits и graph layout. Кнопки «Обновить» в репозитории и «Синхронизировать сейчас» в настройках запускают полный поток, показывают время обновления и сохраняют старый граф при ошибке сети. После создания, удаления или переименования ветки запускается быстрый refresh текущего snapshot.

Как проверить: открыть репозиторий, нажать «Обновить» или кнопку в настройках и убедиться, что появляется время обновления; создать новый репозиторий на GitHub и повторить синхронизацию — он появится в боковой панели; удалить репозиторий на GitHub и повторить синхронизацию — он исчезнет из списка. Затем создать/удалить/переименовать ветку и проверить, что граф и список веток меняются без смены проекта.

### ✅ Подключён лимит коммитов

Описание: `SettingsModal` сохраняет `commitLimit`, и выбранное значение теперь используется при загрузке истории.

Где находится: `src/components/Modal/SettingsModal.tsx`, `src/context/AppContext.tsx`, `electron/preload.cjs`, `electron/main.cjs`.

Что изменено: `commitLimit` добавлен в IPC-контракт `getRepository`; main process проверяет диапазон 25–100 перед формированием GitHub-запроса. При сохранении настроек текущий репозиторий обновляется с новым лимитом.

Результат: выбор 25, 50 или 100 коммитов больше не является декоративным — он влияет на размер загружаемой истории и графа.

### ✅ Состояние графа обновляется после операций с ветками

Описание: после создания, удаления или переименования ветки context запускает общий refresh и обновляет branches/commits/layout.

Где находится: `src/context/AppContext.tsx`, `src/components/Modal/BranchModal.tsx`.

Причина: исправлено через общий `refreshRepositoryData()`.

Результат: пользователь видит актуальный snapshot без смены репозитория.

### ✅ Защищена загрузка README при смене ветки

Описание: `ReadmeModal` теперь принимает ответ только для последнего выбранного branch request.

Где находится: `src/components/Modal/ReadmeModal.tsx`.

Что изменено: добавлен локальный request id, состояние загрузки и защита несохранённого текста. Поле README и сохранение блокируются до завершения загрузки, а смена ветки при изменённом тексте требует сначала сохранить или отменить ввод.

Результат: медленный ответ старой ветки не перезаписывает текущий README.

### 🟠 Ограничение размера папки только предупреждает

Описание: `MAX_TOTAL_SIZE` добавляет warning после превышения 1 ГБ, но файлы продолжают попадать в память и могут быть загружены. Большая папка создаёт высокую нагрузку на память и GitHub API.

Где находится: `electron/main.cjs` (`scanFolder`, `uploadFolderToRepo`, `buildFolderChanges`).

Причина: лимит не является hard limit и обработка идёт последовательно с буферизацией.

Способ исправления: прекращать сканирование/загрузку после hard limit, ограничить размер release asset, добавить потоковую или порционную обработку.

### 🟠 Смешанная кодировка сообщений main process

Описание: часть русских ошибок в `electron/main.cjs` хранится как mojibake (`Р...`) и попадёт пользователю в таком виде; рядом есть корректные UTF-8 строки.

Где находится: `electron/main.cjs`.

Причина: исторически смешанные кодировки в одном файле.

Способ исправления: привести только пользовательские строки к UTF-8, не менять контракт ошибок, добавить тест на несколько сообщений.

### 🟢 Дополнительные проблемы

- `AppContext` — крупный координационный модуль (~693 строки по структуре проекта): при росте функций его стоит разделить по доменам.
- `commitLimit` и отображаемая версия в `SettingsModal` частично дублируют runtime-источник; версия UI захардкожена.
- Модальные окна в основном имеют `role="dialog"`, но не везде есть focus trap, `aria-describedby` и блокировка фонового скролла; `UpdatesModal` не объявляет dialog role.
- Списки GitHub ограничены фиксированными `per_page` и не поддерживают pagination; это станет узким местом для больших репозиториев.
- Поиск отображает результаты, но не даёт перейти к коммиту в графе и не отменяет предыдущий запрос.

# Анализ разработчика

## Оптимизация

Проблема: загрузка папки читает файлы последовательно, удерживает содержимое в памяти и не останавливается на суммарном лимите.

Причина: `scanFolder` и `buildFolderChanges` строят полные in-memory maps.

Решение: hard limit по размеру/количеству файлов, порционная обработка, ограниченная конкуррентность для GitHub blobs.

Ожидаемый эффект: предсказуемое потребление памяти и меньше риск зависания на больших проектах.

Проблема: граф рендерит все узлы и рёбра DOM/SVG и layout сортирует историю целиком.

Причина: текущая модель рассчитана на фиксированные 50 коммитов; настройка лимита пока не работает.

Решение: сначала подключить валидный commit limit и pagination, затем добавить виртуализацию/оконный рендеринг для больших историй.

Ожидаемый эффект: стабильный FPS и меньше время первого отображения.

## Улучшение кода

- SOLID: UI-компоненты в целом разделены по функциям, но `AppContext` одновременно хранит состояние, вызывает API, форматирует результаты и управляет UX. Следующий рефакторинг — по доменам GitHub repository/PR/issues/releases.
- ООП: проект преимущественно функциональный React и модульные функции; вводить классы без необходимости не нужно.
- Дублирование: повторяются проверки `validRepo`, loading/error wrappers и форматирование release/issue UI; нужен общий backend validator/result helper и небольшие UI-утилиты.
- Читаемость: крупные файлы `AppContext.tsx` и `electron/main.cjs` требуют декомпозиции после исправления критических рисков.
- Безопасность: усилить валидацию всех IPC-входов, whitelist скачивания, размер ответов и единый безопасный механизм MCP-сессии.
- Масштабируемость: добавить pagination, AbortController/request ids, интеграционные IPC-тесты и единый GitHub client.

## Новые функции

Название: Pagination истории и GitHub списков

Зачем нужно: 50/100 записей недостаточно для больших репозиториев.

Польза: полная история и предсказуемая нагрузка.

Сложность реализации: средняя.

Название: Безопасный MCP bridge

Польза: рабочая интеграция и меньший риск утечки.

Сложность реализации: высокая.

Как реализовать: отдельный локальный authenticated bridge или явный одноразовый session handoff с минимальными правами.

Название: Обновление repository snapshot после mutation

Зачем нужно: UI должен сразу отражать branch/repository changes.

Польза: меньше рассинхронизации и повторных действий пользователя.

Сложность реализации: низкая.

Как реализовать: общий `reloadCurrentRepository` в context после успешных branch mutations.
